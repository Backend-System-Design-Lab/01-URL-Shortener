# 02. Capacity Estimation

## 1. 기본 가정

URL Shortener는 사용자 수보다 요청량을 기준으로 산정한다.

| 항목          |          값 | 근거                       |
| ----------- | ---------: | ------------------------ |
| 일간 활성 사용자   | 별도 산정하지 않음 | 비로그인 기반 서비스              |
| 일일 URL 생성 수 |       1억 건 | 책의 설계 조건                 |
| 일일 URL 조회 수 |      10억 건 | 읽기:쓰기 = 10:1             |
| 읽기 요청 비율    |    약 90.9% | 전체 요청 11건 중 10건          |
| 쓰기 요청 비율    |     약 9.1% | 전체 요청 11건 중 1건           |
| 평균 요청 크기    |  약 200Byte | URL과 요청 데이터 기준           |
| 평균 응답 크기    |  약 300Byte | 단축 URL 또는 Redirect 헤더 기준 |

요청과 응답 크기는 애플리케이션 데이터 기준이며, 실제 네트워크에서는 HTTP/TLS 오버헤드가 추가된다.

---

## 2. 트래픽 산정

### 일일 총 요청 수

```text
일일 URL 생성 수 + 일일 URL 조회 수
```

계산:

```text
1억 + 10억 = 11억 건/일
```

### 평균 RPS

```text
11억 ÷ 86,400초
≈ 12,731 RPS
```

### 피크 RPS

평균 트래픽의 3배가 특정 시간대에 집중된다고 가정한다.

```text
12,731 × 3
≈ 38,194 RPS
```

* 피크 계수: 3
* 예상 피크 RPS: 약 38,200 RPS

---

## 3. 읽기 및 쓰기 요청

### 읽기 RPS

```text
38,194 × 10 / 11
≈ 34,722 RPS
```

### 쓰기 RPS

```text
38,194 × 1 / 11
≈ 3,472 RPS
```

---

## 4. 저장 용량

### 데이터 한 건의 크기

| 필드           |     예상 크기 |
| ------------ | --------: |
| ID           |     8Byte |
| 단축 코드        |   약 8Byte |
| 원본 URL       | 약 100Byte |
| 생성 시간 및 상태   |  약 24Byte |
| 행 및 인덱스 오버헤드 | 약 110Byte |
| 합계           | 약 250Byte |

### 일일 저장량

```text
1억 건 × 250Byte
≈ 25GB/일
```

### 연간 저장량

```text
25GB × 365
≈ 9.1TB/년
```

10년 동안 필요한 논리 저장 공간은 약 91.3TB다.

책에서 계산한 36.5TB는 평균 100Byte인 원본 URL 문자열만 계산한 값이다. 실제로는 PK, 단축 코드, 인덱스와 메타데이터 공간이 추가된다.

### 복제 및 백업 반영

Primary 1대, Replica 2대, 전체 백업 1개를 가정한다.

```text
9.1TB × 4
≈ 36.5TB/년
```

10년 기준 실제 관리 대상 데이터는 약 365TB까지 증가할 수 있다.

---

## 5. 네트워크 사용량

피크 RPS를 기준으로 계산한다.

### Inbound

```text
38,194 RPS × 200Byte
≈ 7.6MB/s
≈ 61Mbps
```

### Outbound

```text
38,194 RPS × 300Byte
≈ 11.5MB/s
≈ 92Mbps
```

실제 네트워크 사용량은 HTTP Header와 TLS 오버헤드로 인해 더 커질 수 있다.

---

## 6. 캐시 용량

* 캐시 대상: 자주 조회되는 단축 코드와 원본 URL
* 캐시할 데이터 개수: 약 2,000만 건
* 데이터 한 건의 크기: Redis 오버헤드를 포함해 약 300Byte
* 예상 총 캐시 크기: 약 6GB
* 여유 공간 반영: 약 8GB
* TTL: 24시간 + 임의 만료 시간
* 예상 Cache Hit Ratio: 80% 이상

캐시 크기와 Hit Ratio는 실제 접근 패턴을 측정한 뒤 조정한다.

---

## 7. 메시지 처리량

현재 범위에서는 메시지 브로커를 사용하지 않는다.

클릭 통계와 데이터 분석 기능을 구현할 경우 Kafka 등의 메시지 브로커 도입을 후속 과제로 검토한다.

## 8. 예상 병목

| 컴포넌트           | 예상 병목                  | 확인 지표                           | 대응 방법                    |
| -------------- | ---------------------- | ------------------------------- | ------------------------ |
| Application    | 요청 증가에 따른 Thread 대기    | CPU, Thread, p95                | 무상태 서버 수평 확장             |

| Message Broker | 현재 사용하지 않음             | -                               | 클릭 분석 도입 시 검토            |
| External API   | 현재 사용하지 않음             | -                               | 악성 URL 검사 도입 시 검토        |

## 10. 로컬 실험 규모

운영 규모를 로컬 환경에 그대로 재현하지 않고, 동일한 조건에서 구조별 상대 성능을 비교한다.

| 항목           | 실험 규모                          |
| ------------ | ------------------------------ |
| 데이터 수        | 10만 → 50만 → 100만 건             |
| Virtual User | 20 → 50 → 100 → 300            |
| 요청 유형        | URL 생성, 일반 조회, Hot Key, 잘못된 코드 |
| 비교 지표        | RPS, p95, p99, 오류율, DB 조회 수    |
| 비교 구조        | DB Only → Redis 적용 → 추가 개선     |

모든 개선 전후 실험에서는 데이터 수, VU, 실행 시간, JVM 옵션과 Docker 자원 조건을 동일하게 유지한다.
